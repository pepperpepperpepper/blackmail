# Blackmail — performance review

**Nothing here was measured on his iPad, or on any iPad.** The device and its tunnel are offline. Everything below is either (a) read from the source as it stood on 2026-09-22, (b) measured on this Linux host by running the real library code in release builds, or (c) reasoned about UIKit/Foundation behaviour from the iOS 16.5 SDK's own interface files. Where a host number does not transfer to Darwin I have said so and thrown it away rather than quote it.

One calibration that matters and cuts against most of the raw numbers: **this host is a server-class Zen 2 core, which is roughly A12-class on single-thread integer work.** The instinct to multiply host timings by 3-5x for "an old iPad" is wrong. Read the host figures as 1-1.5x, not 3x. Several findings were originally sized with the bigger multiplier and shrink accordingly.

The second structural fact, and it is the good news: **`TLSConnection`, `IMAPClient`, `IMAPMailRepository` and `SMTPClient` are all plain actors with no `@MainActor` anywhere in `Sources/Blackmail/Mail`, `/IMAP`, `/Net` or `/SMTP`.** I looked for main-thread blocking first because a frozen screen is the worst outcome for this user, and there is essentially none. Nothing in this review can produce a frozen screen. That is a deliberate architectural property and it is the single biggest thing this codebase got right. It also means the review is about *latency and unexplained waiting*, which is the second-worst outcome, not the worst.

## Fix now

### 1. The reading pane shows the PREVIOUS letter for the whole fetch
`ios/Sources/Blackmail/UI/MessageDetailViewController.swift:165-179`

`show(summary:)` sets `placeholder.isHidden = true; header.isHidden = false; webView.isHidden = false` and then suspends on `await repository.loadMessage(...)`. Both `header.configure(with: m)` (:177) and `render(m)` (:179) are after the await. For the whole fetch the pane holds the previous letter's header and body — intact, coherent, and belonging to a different row — while the list selection bar has visibly jumped to the new row.

**Cost:** one IMAP round trip plus a full `BODY.PEEK[]` (`IMAPMailRepository.swift:675-690`), serialized behind anything already on the single connection and behind the same tap's `UID STORE \Seen`. There is no message cache — `lastBody` (:46) is read only by the attachment path at :1148 — so re-opening the same letter refetches it. Roughly 0.2-0.5 s for an ordinary letter, several seconds for one carrying a scan. CPU is not the story: I confirmed decode at 1.7 ms (16 KB) to 10 ms (4 MB), all off-main.

**Why it is first:** this is the #1 action in the product, every single-letter row goes through it (`MessageListViewController.swift:1170-1185` sends `count > 1` to `show(thread:)` and everything else here), and the failure mode is worse-shaped than a blank pane — the pane and the selection *disagree*, and the content is a plausible wrong letter. There is a second manifestation: `showEmpty()` (:149-161) only hides the web view, never loads a blank document, so after a delete or a folder switch the next tap **re-reveals the letter he just deleted** until the fetch lands.

**What to change:** before the await, configure the header from `summary` (sender, subject, date are all in hand) and load a one-line "Loading…" document. `show(thread:)` at :229-246 already does exactly this and its comment explains why. The compromise is that `MessageSummary` has no `to`/`cc`, so the header reads "To: me" briefly — `show(thread:)` already makes that same trade with `to: [], cc: []`. Loading the notice into the web view fixes the stale-document case for free.

**What it buys:** removes the app's most-hit instance of unexplained waiting, and removes a class of "wrong letter on screen" that reads as data corruption. `docs/INVESTIGATIONS.md` ("The empty letter that was a dropped connection") already asserts this behaviour exists — the docs describe code that was never written.

**What landed.** Both reading-pane paths go through `PaneLoads.show`, which draws the stand-in, the row's sender, subject and date over "Loading…" (`Message.heading(for:)`, `PaneNotice`), before the body is asked for, so the code now does what B-023 and the investigation described. Emptying the pane loads an empty page into the web view as well as hiding it, so the letter just binned cannot be unhidden by the next tap. Two corrections to the estimate above. The tap's FETCH does not always wait behind its own STORE: the pane's task starts first and the two race for the connection, and on the scripted server either can win, so it is up to a round trip better than stated. And the pane now also keeps its fetch, so a letter he taps past is called off rather than downloaded whole before the one he stops on. A fetch already on the wire finishes its exchange and is thrown away; one still waiting leaves the line without sending anything; neither draws (`PaneLoads.draws`, the `SearchAnswer` rule). Read marks are not called off: a letter tapped and left counts as read, as in Mail, so the letter he stops on waits for the STOREs of the unread ones he tapped past, one round trip each. `PaneLoadsTests`; B-041.

### 2. `RecipientBook` re-encodes and rewrites the entire address book once per harvested address
`ios/Sources/Blackmail/Mail/RecipientBook.swift:92` (and the caller, `IMAPMailRepository.swift:410-414`)

`record()` ends with an unconditional `evictIfNeeded(); save()`, and `save()` (:170) is `JSONEncoder().encode(Array(entries.values))` + `defaults.set` over the whole 300-entry book. No dirty flag, no early-out for a known address (`entry.lastSeen = Date()` mutates every time). The caller harvests `env.from + env.to + env.cc` per row inside the `compactMap` that builds the page.

**Cost, device-honest:** ~1.2-1.3 ms per call, essentially all of it `JSONEncoder` over ~29-37 KB. Four independent measurements on this host converged on this. **I am deliberately discarding the UserDefaults component** (another 2.5-3.4 ms/call here): it is a swift-corelibs artifact that scales linearly at ~11 MB/s in the *value* size and writes no file, whereas Darwin's `UserDefaults.set` drops a retained immutable `Data` into CFPreferences' in-memory domain with a coalesced push to cfprefsd. That is why `synchronize()` has been a documented no-op since iOS 7. Roughly 70% of the first headline figures for this finding do not exist on iOS.

That leaves, at ~2-2.5 addresses per message on a personal mailbox: **~150-190 ms per 50-row page here, order 0.3-0.5 s on his iPad.** The search path is worse: `startSearch` runs `binnedHits` over Trash and Spam at `maximumBinnedHits = 200` each (`IMAPMailRepository.swift:968, 1073`) through the same loop, so a wide All-Mailboxes search can reach ~1000+ calls — seconds — before the first result row is assembled.

**Why it is second:** it is the only thing in the review that lands on *all three* of the things he does hundreds of times a day, it is unbounded, it repeats on every folder open and every page, and the fix is trivial. It is not a stall (repository actor), it is dead time between "the server answered" and "the rows are on screen".

**What to change:** take `save()` out of `record()`; set a dirty flag and flush once — at the end of `summaries()`, or on `willResignActive`. Add a batched `note(contentsOf:)` so the page's addresses go over in one call. `used()` (:72, once per send) can keep flushing eagerly. Measured: ~150-190 ms/page → ~1.3 ms/page. Losing one page of passively-harvested addresses to a kill costs nothing; it is re-harvested next load. **Do not** hoist the `JSONEncoder` to a stored property — measured 1.2363 vs 1.2344 ms, i.e. nothing. Batching is the entire fix. The eviction sort does not matter either; it is 0.0125 ms.

**While you are in that file — a correctness bug, not a perf one.** `RecipientBook.shared` is a `final class` (:43) whose `entries` dictionary (:56) is mutated from the repository actor (`IMAPMailRepository.swift:412, :825`) and read on the MainActor (`ComposeViewController.swift:441`, per keystroke). `Package.swift` is pinned to tools-version 5.9 so the compiler never flagged it. This was **reproduced**: a scratch copy with one thread noting and one suggesting SIGSEGVs 8 out of 8 runs, crashing in `suggestions(for:) → _copyCollectionToContiguousArray → swift_retain`. Real-world odds are low (the unsafe window is 0.35 µs of a ~1.3 ms `record()`, and a throttled reader at his typing rate survived 236,409 writes clean) — order once a year, not a stall. **Fix it with an `NSLock` around the dictionary read/insert only.** Do *not* hold the lock across `save()` (that puts a 5-8 ms encode on a contended keystroke — you would trade a yearly crash for a per-keystroke hitch in the exact interaction you are protecting), and do *not* make it an `actor` (that forces `suggestions(for:)` async and the suggestion rows appear a runloop turn late).

**What landed**, for both halves. `note()` marks the book dirty and nothing more; the repository flushes once for each set of rows it builds, which is where every page, jump and binned search result goes through (`IMAPMailRepository.rows(from:…)`), `used()` still writes at once, and the app writes whatever is left in `applicationDidEnterBackground`. The `JSONEncoder` is not hoisted. A 50-row page is one write where it was a hundred, and a search everywhere is one per mailbox its rows came from (`RepositoryTrafficTests`). Release build on this host, a full 300-entry book and a page's hundred addresses: 4.5 ms against 382 ms, and the part of the old figure that transfers to the device, the encoding, was about 128 ms of it. The lock is an `NSLock` around the dictionary and the dirty flag only: a note holds it for the insert, a keystroke for the copy, and a flush for the copy, never for the encode or the write. Flushes queue behind a second lock that nothing on the keystroke path takes, so two at once cannot leave the older copy on disk. `RecipientBookTests` notes on one thread while another asks for suggestions, and while another flushes; with the lock taken out of either side it crashes every run (8 of 8, and 30 of 30 for the flush). A third test holds one flush in the middle of its write while a second starts; without the flush lock the older copy is the one left on disk.

### 3. Delete one of the two cold-launch inbox reloads
`ios/Sources/Blackmail/UI/RootViewController.swift:141`

`RootViewController.viewDidLoad` awaits `list.reload()`, and `MessageListViewController.viewDidLoad` already fires its own `Task { await reload() }` at :334. Both force the nav's root view to load (`setToolbarHidden` at :86, `addSubview(child.view)` at :101), so the list's task is enqueued first, and `mailboxList.select(mailboxID:)` uses `selectRow` and does not fire `onSelectMailbox` — so :141 reloads the same instance a second time. Nothing dedupes: `reload()` has no in-flight guard and `listMessagesOnce` re-issues `searchAll()` whenever `beforeUID == nil` (`IMAPMailRepository.swift:334`). This was inherited when `openMailbox(...)` was swapped for `select` + `await list.reload()`; no comment defends it.

**Cost:** 4 duplicated serialized round trips (~320 ms at 80 ms RTT) and 170-620 KB of duplicated download per cold launch — `UID SEARCH ALL`, one 50-row `UID FETCH`, two preview `FETCH`es (the repo's own comment at `IMAPMailRepository.swift:567` puts previews at 100-400 KB). The socket stays busy for the first seconds after launch, so his first tap on a letter queues behind mail he already has.

**Two harms beyond the wasted bytes, and they are the reason this is in "fix now" rather than lower:** `reload()` assigns `messages = first` with `preview: ""`, so **previews that already landed visibly blank out and refill**; and `reload()` calls `searchBar.clear()`, which nils the field *and* resigns first responder — so **a search he starts typing in the first seconds after launch is erased with the keyboard dismissed.** He picks the iPad up many times a day and searching is his documented habit.

**What to change:** delete line 141. One line. Do **not** instead delete the VC's own Task at :334 — `openMailbox()` (:295-300) only does `setViewControllers` and relies entirely on the new VC's `viewDidLoad` to load anything, so that would break every folder tap.

## Fix before he gets it

### 4. The Send path burns ~2 s of pointless CPU on a photo letter, with no feedback at all
Two findings, same tap, fix them together.

**4a. `SMTPClient.dotStuffed` walks the built message a byte at a time through `Data`** — `Sources/Blackmail/SMTP/SMTPClient.swift:390-415`, one caller, once per send. Measured against real `RFC5322Builder` output on this host: 1 MB attachment (1.44 MB raw) 168 ms; 5 MB (7.2 MB raw) 863 ms; 20 MB (28.7 MB raw) 3464 ms. That is **80-84% of all local CPU in the send path — 5x the entire MIME build including base64 encoding.** I checked the obvious escape hatch: cross-compiling this exact function for `arm64-apple-ios16` against the ios165 SDK leaves per-byte non-inlined calls to `Data._Representation.replaceSubrange(_:with:count:)`, `__DataStorage._bytes`/`._offset`, and a `CollectionOfOne<UInt8>: ContiguousBytes` witness lookup. Darwin's subscript is `@inlinable` and inlines *to these calls anyway*. The host number is representative or conservative.
→ Rewrite with `raw.withUnsafeBytes` into a preallocated `[UInt8]`, or scan for line breaks and `append(contentsOf:)` whole runs. Measured 126→3.0, 625→13.2, 2506→35.7 ms (40-70x), **byte-identical output**, and it touches none of the documented CRLF-normalisation / dot-stuffing / CRLF-pair-swallowing invariants.

**4b. `RFC5322Builder.uniqueBoundary` substring-scans every attachment's base64 payload** — `Sources/Blackmail/MIME/RFC5322Builder.swift:658-669`. `candidates` (built at :118-132) carries every attachment's wrapped base64, and `contains(where:)` cannot short-circuit when there is no collision. One pass over the 14.3 MB base64 of a 10 MB photo is 201 ms; `uniqueBoundary` is 604-610 ms of a 726-779 ms `build()` (82%), or 1211 ms of 1496 ms for five 4 MB photos. **The scan is provably vacuous over exactly the candidates that cost anything:** the boundary always contains `_`, `Data.base64EncodedString()` uses the standard alphabet so `_` never appears (verified, 0 occurrences in 14.3 MB), and quoted-printable escapes `0x3D` unconditionally so its output can never contain `=_` (verified by feeding it text stuffed with `=_`). Only the short filenames/mimeTypes/contentIDs could ever match, and those are free.
→ Drop the payloads from the candidate list, or keep the guarantee and scan bytes: a hand-rolled memmem over the UTF-8 view does the same 14.3 MB pass in 8.9 ms vs 201 ms. Do **not** "scan the decoded source `Data`" — the comment at :73-76 deliberately requires the check to be against the *encoded* payload. It is two calls today, three once the planned inline signature logo lands.

**4c. And the part that actually matters to him: there is no feedback.** `ComposeViewController.sendTapped` (:539) collects and awaits. No spinner, no disabled button, nothing — I grepped `UIActivityIndicatorView|ProgressView|spinner` across `ComposeViewController.swift` and `RootViewController.swift` and got nothing. `PHPicker` `selectionLimit = 5` at :300 and the comment at :317-322 deliberately keeps full resolution, so five iPad photos is a 28 MB raw message. Today that is ~3.5 s of local CPU here (order 5 s on his device) *plus* the upload, with a live compose sheet and a Send button he can press again.

**What 4a+4b buy together:** local CPU on a photo send drops from ~2 s to under 50 ms, so the wait becomes honestly just the upload. Add a disabled Send button and a progress state and this stops being a "did it work?" moment.

### 5. `MIMEDecoder.decodeBase64` accumulates into `Data`, not `[UInt8]`
`ios/Sources/Blackmail/MIME/MIMEDecoder.swift:53`

`var out = Data()` with per-byte `out.append(...)`, directly above `decodeQuotedPrintable`, whose comment at :88-93 documents having learned exactly this lesson. Three independent release-build measurements agreed to within 2%: 1 MB 124-127 ms, 5 MB 624-626 ms, 25 MB 3122 ms. **This is not a third quadratic** — scaling is exactly linear 1:5:25, so the file's two prior O(n²) fixes hold and this is a constant factor. It is also not a Linux artifact: iOS 16.5's `Foundation.swiftinterface` declares no `Data.append(_: UInt8)`, so it resolves through `RangeReplaceableCollection` → `CollectionOfOne` → `_Representation.replaceSubrange`, which is `@usableFromInline` with no body — an opaque cross-module dylib call per byte. iOS cannot be faster than the specializable Linux path.

**Where it bites:** opening an attachment (`fetchAttachmentData` → `decodeTransfer`: a 5 MB PDF is ~625 ms here) and opening a letter with inline pictures (a 2.3 MB `multipart/related` with 8 `cid:` images is 210 ms of decode, of which 196 ms is this loop). It does **not** touch list scrolling — previews are capped at 2048/8192 bytes (`IMAPMailRepository.swift:559, 571`) — and it does not touch opening a plain letter with a big attachment, because `flatten` only decodes the chosen text parts.

**What to change:** `var out: [UInt8] = []`, keep the `reserveCapacity`, `return Data(out)`. Three lines, 5.7x, output byte-identical across 1/5/25 MB and all 366 tests pass. (The first estimate of 8.6-11x also requires wrapping the input in `withUnsafeBytes`; do that too and it is ~11x.) **Better, if someone wants to spend 20 more minutes:** `Data(base64Encoded:, .ignoreUnknownCharacters)` does 5 MB in 6.0 ms — 104x. The doc comment's leniency argument is real and load-bearing (I confirmed `"QQ==QQ=="` → hand `4141` vs Foundation `41`, and `"QUJDR"` → hand `414243` vs Foundation `nil`), but a cheap scan for an interior `=` plus a `length % 4` check routes those to the existing hand loop and preserves every case.

### 6. Cold launch reaches `SELECT INBOX` about eighteen commands deep
`Sources/Blackmail/Mail/IMAPMailRepository.swift:214-222` and `Sources/Blackmail/UI/RootViewController.swift:139`

`resolve()` does `if roleNames.isEmpty { _ = try await listMailboxes() }` *before* the two lines that would hand back `"INBOX"` for free, and `listMailboxes()` is `LIST "" "*"` plus `client.status(name, items: ["UNSEEN"])` per selectable folder in a serial loop (:277) — 8 folders on this account. It throws the result away (`_ =`); it only wanted a name. And because the sidebar's sweep at `RootViewController.swift:139` is in flight concurrently with the list's own task, and there is no memoization or in-flight guard, **cold launch fires the whole sweep twice and they interleave at the exchange gate.** The `SELECT INBOX` lands around wire position 18 instead of 2 — roughly 1.4-2.2 s of round trips at 80-120 ms RTT, in front of a blank middle pane. This is once per process only; `roleNames` is never cleared.

**What to change — and note the obvious fix does not work.** Swapping lines 139 and 141 moves nothing, because `list.reload()` still goes `listMessages → select("inbox") → resolve → roleNames.isEmpty → listMailboxes()`. The real change is to split what `listMailboxes()` conflates: give the repository a **LIST-only role path, memoized, with an in-flight guard so two racing callers share one sweep**, have `resolve()` use it, and deliver the unread counts in a second pass that patches the sidebar in place. One caveat: with `roleNames` still empty, `countedFolders(labels:selected:)` (:521, called at :435) builds `countedFolderIDs` without `roleNames[.archive]`, so reading one of the first 50 letters would decrement Inbox but not All Mail — the exact drift the comment at :501-520 exists to prevent. The LIST-only path (which does populate roles) avoids this; an unconditional `return "INBOX"` would not.

**What it buys:** time-to-first-mail becomes connect + 1 LIST + SELECT/SEARCH/FETCH. Combined with #3, cold launch should roughly halve.

**What landed.** `resolve()` asks for LIST alone, remembered, and a LIST already on the wire is joined rather than sent again, so the folder pane's names and the Inbox's role share one. The roles are filled from it, `folderForAttribute` included, so the caveat above does not arise. At launch the folder pane draws the names from that LIST, and its sweeps are held until the Inbox's first page has been tried (`SweepCoalescer`, released by `MessageListViewController.onFirstLoadFinished`). On the scripted server a cold launch is now LOGIN, LIST, `SELECT "INBOX"`, `UID SEARCH`, `UID FETCH`, then LIST and a STATUS per folder, where the Inbox's SELECT used to follow every STATUS (`RepositoryTrafficTests`). The sweep's LIST is a second one, a second or so after the first; reusing the first would save one background round trip per launch and was not worth a clock. The held sweep is let go only if the first page came: after a failed one it would connect again at once, which the client treats as a fresh attempt, so a refused password would go twice and an unreachable server would cost two connect timeouts. The sweep itself has one read retry, the LIST's inside `freshListing`; a second around the whole sweep would turn a failed reconnect into two.

### 7. `LayoutAudit` ships, and it is the only main-thread periodic work in the app
`Sources/Blackmail/App/AppDelegate.swift:50`, `Sources/Blackmail/UI/LayoutAudit.swift:138`

**This one is mine, and I cannot measure it, which is exactly why it is here.** `LayoutAudit.beginSweeping()` is called unconditionally from `application(_:didFinishLaunchingWithOptions:)`. I grepped the entire `Sources/Blackmail` tree for `#if DEBUG` and there is not one. So on his iPad, every launch, a 2-second repeating timer runs 90 `@MainActor` passes that walk the whole window tree calling `hasAmbiguousLayout` on every view.

Per-view `hasAmbiguousLayout` is probably tens of microseconds, so a few hundred views is likely single-digit milliseconds and invisible. But it is main-thread, it is unmeasurable from here, it runs during **precisely the three minutes of cold launch and first scrolling** that matter most, and it has zero value on his device. The file's own comment reasons carefully about not letting the timer tick at bedtime, which is the right instinct applied one step short: it should not tick on his iPad at all.

**What to change:** wrap the call in `#if DEBUG`, or gate it on the same switch as the diagnostics screen. One line, removes the only main-thread periodic work in the product, and costs nothing — `sweepNow()` stays available from the diagnostics screen for whoever is developing.

## Record and leave

Each of these is real. None is worth changing working code for right now, and several have fixes that are net-negative as first proposed.

- **Whole-message `BODY.PEEK[]` on every open** — `IMAPMailRepository.swift:680`. Real for multi-megabyte mail (a 5 MB scan is ~6.9 MB and holds the single connection throughout; since #1 landed, only when it is the letter he stops on or the one already on the wire as he taps on), but the obvious fix is a regression: `previewParts[id]` does **not** cache the BODYSTRUCTURE (`rememberPreviewPart` at :582-585 keeps only the chosen leaf, and the comment at :570-576 says keeping trees was deliberately rejected), inline images are **free today** because `fetchAttachmentData` short-circuits on `lastBody`, and forwarding depends on the same thing (:842-844, and `INVESTIGATIONS.md` ("Forwarding now carries the files") records eager attachment loading being "rejected twice over"). If this ever gets touched, the right shape is a size gate: `RFC822.SIZE` is already on the wire (`IMAPClient.swift:46` → `MailWireTypes.swift:86`) and thrown away at :422-435. Remember it, take a section path above a megabyte or two, keep the single round trip below. Fixing #1 removes most of what he *feels* here for free.
- **`fetchAttachmentData` re-parses the whole message per inline image** — `IMAPMailRepository.swift:1149`. Real, but it is 6-30% of the path; the other 70-94% is the base64 decode that #5 fixes. On the case he actually hits daily (a signature block with 1-4 logos) the whole saving is 0.5-4 ms. And the naive cache retains a *second full copy* of the message beside `lastBody` — 31 MB becomes 62 MB at Gmail's ceiling — because `parse` fills `bodies[section] = Data(bytes[bodyRange])` with real copies. Only worth doing as part of a parse-by-slice change. Also: "WebKit asks for one `bmcid://` at a time" is wrong; `InlineImageLoader.webView(_:start:)` spawns a Task per resource and the serialization is the actor's.
- **`TLSConnection` read buffer never returns its high-water allocation** — `TLSConnection.swift:159-166`. Confirmed with honest RSS methodology (`malloc_trim` + forced mmap): a 25 MB literal leaves ~25 MB attached to a buffer whose `count` is 40, and across 1/8/25/3/1/12 MB literals it **ratchets to +52 MB**, held until Gmail drops the idle socket (nothing in the repository ever disconnects). On top of `lastBody`'s deliberate second copy. On a 2-3 GB iPad this raises background-jetsam odds and therefore cold relaunches. The fix is one line — `let out = Data(buffer.prefix(count)); buffer = Data(buffer.dropFirst(count))` — and it is genuinely free (retained capacity buys 0.2 ms on a 25 MB append). Two corrections to the first write-up: it does **not** kill the 2x peak (both forms peak at +25 MB; that is inherent), and the `if buffer.isEmpty { buffer = Data() }` alternative is a **provable no-op** — after a literal the tail is `)\r\n`, so it never fires. **What landed** (now in `Net/ReadBuffer.swift`, which `TLSConnection` reads through) is that same one-liner, and it is not a no-op, because it also runs after every *line*: the no-op argument holds only for the literal call site. A literal is followed by `)` and the tagged line, so the buffer is empty once that tagged line has been read, which is where almost every exchange ends, and that is where the storage goes. `ReadBufferTests` checks it.
- **`readLine()` rescans the buffer for CRLF after every chunk** — `TLSConnection.swift:147`. Genuinely quadratic, confirmed (0.31/2.06/18.4/242 ms at 64 KiB/256 KiB/1 MiB/4 MiB), and worse than modelled because `fill()` uses `minimumIncompleteLength: 1` so real chunks are 4-16 KiB, not 64 KB. But at his likely mailbox size it is single-digit to low-tens of milliseconds on a background actor. **The obvious fix is wrong and would corrupt the stream:** `max(0, buffer.count - 1)` is a count, and `Data.removeFirst` leaves `startIndex` non-zero (measured: 100 after `removeFirst(100)`), which is precisely why the existing code writes `buffer.startIndex` everywhere. Resuming at `count - 1` skips a CRLF and desyncs IMAP — the failure `performCommand`'s own comment warns about. It must be `endIndex - 1` and must reset inside `read(exactly:)`.
- **`IMAPParser.tokenize` materialises every line as `Array<Character>`** — `IMAPParser.swift:69`. Only material at tens of thousands of UIDs (6.8 ms at 5k, 83.6 ms at 60k), and his actual folder sizes are unverified. Note `Array(line.text)` is only ~10% of it; the bulk is `scanAtom`'s per-Character String building. If ever done, a naive digit scanner is a **regression**: `result.untagged` carries every untagged line, and I confirmed the naive version turns `* SEARCH 1:5` into `[1,5]`, keeps the MODSEQ trailer, and picks up `* 4231 EXISTS`. The keyword gate, range expansion and trailer skip at :440 must survive.
- **`Diagnostics.redact` runs two `NSRegularExpression` passes on every response line** — `Diagnostics.swift:38-44`, unguarded in release. Most of the alarming host number (78% of the 60k-UID figure) is `trimmingCharacters` materialising an NSString copy on corelibs; Darwin's bridge is zero-copy. The iOS residue is ~10 µs fixed per line plus ~12 ns/byte, i.e. 3-4 ms per 50-row page. Also, it does **not** bite the search he does constantly — only `listMessagesOnce` with `beforeUID == nil` and `messages(around:)` call `searchAll()`. Free wins if anyone is passing through: hoist the two regexes and the `CharacterSet` into statics (14 µs → 3.9 µs per line, byte-identical), and log `* SEARCH {N uids}` the way literals already log as `{N bytes}` — that one line can be 288 KB of a 500-entry transcript.
- **`DateFormatter` built on every `listTimestamp` / `detailTimestamp` call** — `MailModels.swift:372, :469`, called twice per row and once per letter in `ConversationDocument`. Real waste (114-127 µs/call), but an iPad list pane shows 8-10 rows at a fixed 96 pt height, so a `reloadData` is ~2.9 ms and the worst case — a mid-scroll page append — goes from ~5.0 ms to ~2.9 ms and keeps its hitch. `IMAPParser.swift:1011` already caches formatters with exactly the right comment; this is the same lesson unapplied to the display path. Two caveats if fixed: a `static` DateFormatter freezes `TimeZone.current` at first use and needs an `NSSystemTimeZoneDidChange` observer, and do **not** gate the accessibility label on `UIAccessibility.isVoiceOverRunning` — that breaks Switch Control, Voice Control and Braille for the one user who might need them. (Computing `thread.participants` once instead of twice, `MessageListViewController.swift:1157-1164`, is free and correct.)
- **Multi-select delete/move is one round trip per message** — `MessageListViewController.swift:883, :950`. Occasional Edit-mode path, and the real arithmetic is ~46 round trips today vs ~17 after batching (the sidebar sweep and list reload survive), i.e. 2.5x, not 30x. The `applyRead` half is already guarded by `where m.isRead != read`. And batching the destructive half is actively risky: `IMAPClient.move` is commented as "the one sequence in the client that can destroy mail", and a set-based COPY is atomic per RFC 3501, so today's `try?`-per-message costs one message where a batch would abort the whole delete silently. **If anything here, do only the `setRead` batch** — pure `UID STORE` over a sequence set, no destructive fallback. Genuinely worth noting: `loadNextPage` appends with no cap (:553), so Select All after several pages is 150+ serialized operations with no spinner in the edit path.
- **`CaptureProbe` writes a transcript to `tmp/` on every send and nothing deletes it** — `CaptureProbe.swift:56`, deliberately outside `AttachmentStore.purge()`'s reach (the only `removeItem` in the tree is `AttachmentStore.swift:72`). Realistic size is 57-290 KB, median ~110 KB, not the 335 KB first estimated — real traffic dilutes long FETCH lines with PAIR notes, preview lines and literal markers. And `tmp/` is purgeable space that iOS reclaims under pressure before surfacing "out of space", and a WKWebView mail client on a 3 GB iPad gets jetsammed regularly, so the not-running precondition is met most days. Keep the last ~10 at `beginSession()` when convenient; it preserves the documented intent.
- **Detail-pane `onNeedsListRefresh` triggers a full reload plus the 9-round-trip sidebar sweep** — `RootViewController.swift:219-229`. *Superseded: this was wider than recorded here, and it has been fixed.* Delete and Move fired it too, not only Flag and an unread letter opened in a conversation, and it did wipe a search: `reload()` clears the search field whatever the rows are grouped by. The callback is gone. Delete, Move and Flag from the pane edit the list's rows in place and ask for a sweep only when a count may have changed and the arithmetic cannot say by how much (`PaneActions`); an unread letter binned comes off its folders' counts through the same once-only billing as a read (`ReadBilling`, which is what `countedRead` became); and an unread letter opened in a conversation is marked read through the list's own path, the `markRead` entry point this note asked for (`MessageListViewController.markRead`). A letter taken off the list is hidden rather than cut from its arrays, because paging reads its place from them (`RemovedLetters`), and a page short of one binned further down than the list has paged is made up from below, so it does not read as the end of the folder. The list's letters and these edits are in `ListLetters`, which the tests drive; the controller groups and draws. Whatever reloads remain carry the previews already drawn across by id (`ListLetters.fetchedAfresh`). `PaneActionsTests`; B-041.
- **No loading state at launch; the toolbar says "Updated Just Now" before any mail exists** — `MessageListViewController.swift:267, :317`. Every code claim is true, but the removable cost is 0 ms — the 1.5-3 s is round trips, and the main thread is free the whole time (search field takes keystrokes, Refresh/Settings/Edit all respond, folder pane scrolls). It is a UX ticket, not a performance one. The genuinely removable waste on that exact path is #3. (Launch still says "Updated Just Now". A list opened to jump to a day says "Going to <day>…" until the day lands, and so does a jump from the Go to Date sheet, which now starts at the tap rather than after the sheet's third of a second on its way out; a Move says "Moving…". `StatusLine`; B-042.)

## What is fine

This is not a codebase with a performance problem. I went looking for main-thread blocking, for a third `MIMEDecoder` quadratic, for unbounded caches, for layout thrash and for per-keystroke network, and found none of them. Specifically:

- **The concurrency architecture.** Every network and parsing layer is a plain actor with no `@MainActor` leakage. That is why this entire review contains zero frozen screens, which for this user is the whole ballgame.
- **Preview byte caps.** 2048 bytes plain / 8192 bytes HTML (`IMAPMailRepository.swift:559, 571`) means scrolling the list never pulls a body. This is the single best decision in the networking layer for how he uses the app, and it defuses several findings that would otherwise be severe — the base64 decoder costs 0.23-0.92 ms per row instead of tens of milliseconds.
- **No third quadratic in `MIMEDecoder`.** I checked. Base64 scales exactly linearly 1:5:25. The two documented O(n²) fixes hold and what remains is a constant factor.
- **Search input is properly debounced** with a cancelling `Task` (`MessageListViewController.swift:1010-1022`). No per-keystroke network on the thing he does most. (Until the transport's cancellation fix, the cancel itself cost the connection: the superseded search's read dropped its reply and the socket was torn down, so each key after the first reconnected. Now a cancelled search finishes the command it has on the wire and stops, on the same connection; `RepositoryWireTests` types a search at a key a second and checks exactly that.)
- **Fixed 96 pt row height, visible-only `cellForRowAt`.** No self-sizing measurement pass, no layout thrash on a long list — the classic way a mail list dies on old hardware, avoided. (The page loaded above after a date jump no longer leans on it for its scroll correction, the row count times the height, which was out by a row for every conversation on screen that newer mail joined. The rows on screen are held by their letters across every regroup, and measured with `rectForRow`. `ListPlace`; B-042.)
- **`uidListing` caches the UID snapshot across pages**, so scrolling does not re-SEARCH. The re-read is per *listing*, not per page.
- **Threading keys off Gmail's `X-GM-THRID`** with unique keys for blank subjects, so the runaway-merge blowup that wrecks other clients' thread views is structurally closed.
- **`ConversationDocument` as one WKWebView document** is the right call and I would not revisit it. Per-letter web views on an A10 would be far worse than anything in this review. (Two things around it were not right, and both left a letter on "Loading…". A body that came before the stack's document had finished loading was run against the page before it and lost; bodies now wait for `didFinish`. And nothing answered when iOS ended WebKit's content process for memory, so the pane could come back black; it is now drawn again from the letters it holds, with no letter fetched again, once the app is in front and the pane on screen. `PaneDocument`; B-042. The redraw costs one document load, the same as opening the letter, plus the inline pictures of a conversation's letters, which only the last letter downloaded serves from memory. It happens only after a termination, which the connection log now counts, and not a third time if the redrawn page is lost again within seconds, so a letter WebKit cannot hold does not loop.)
- **The single exchange gate in `IMAPClient`** is correct for one socket. Do not "fix" it by making the STATUS sweep concurrent — on one connection that buys exactly nothing. (Still one gate, now with two lines: the letter he opens, the attachment he taps, the first page of a folder he opens, refreshes or jumps to a day in, and his writes go ahead of queued previews, later pages, sweeps and searches, and never interrupt the exchange on the wire. What it did not do was keep a UID command with its SELECT: the two took the gate separately, and another screen's SELECT between them sent the command to the wrong mailbox, B-039. They now go in one hold, and so does each first page, its SEARCH and FETCH together. An All Mailboxes search takes the gate once for Trash, Spam and All Mail, where each of the eight commands up to All Mail's SEARCH used to queue behind every other screen's; its first page's FETCH is a hold of its own after that. It gives way between mailboxes, and only to the interactive line. That is the trade: a letter or a folder opened mid-search waits for the rest of the mailbox the search is in, one SEARCH and, in Trash or Spam, the binned summaries, where it used to wait about one command, and background work waits for the whole search where it used to take turns with it. A list that is replaced, refreshed or jumped cancels its search, which then stops after the command on the wire. A letter opened while a first page is on its way waits for that page. A Delete from the reading pane no longer triggers one (B-041). A write after 90 s of quiet is two holds, the NOOP and then the write, so one queued background exchange can go between them. The binned summaries are still fetched whole, as B-011 decided, and the search's commands are not pipelined; `IMAPClient.search(_:across:)` and `startSearch` say why. `MailboxAtomicityTests`, `ExchangeGateTests`.)
- **`markReadIfNeeded` clears the unread dot locally before any network**, and the `countedRead` set (`MessageListViewController.swift:1265-1271`) already solves the double-billing bug that a naive unread-count optimisation would reintroduce.
- **`AttachmentStore.purge()` at launch** bounds attachment disk, with a comment that reasons correctly about a device that is never restarted.
- **The house pattern for formatters already exists** (`IMAPParser.swift:1011`) with the right calibration written down. It just was not applied to the display path.
- **No persistence layer** means no migration, corruption or staleness bug class. The cost is cold fetches, which is a deliberate and defensible trade for one user with one device.
- **366 tests in ~2 s**, and every proposed byte-level rewrite in this review was verified byte-identical against them on this host.

## What would change most if it were measured on his actual iPad

1. **`RecipientBook` (#2).** The entire device-relevant number is one assumption: that Apple's `UserDefaults.set` of a 30 KB blob, 150 times a page, really is microseconds because CFPreferences stores by reference and coalesces to cfprefsd on a timer. That is well-founded (it is why `synchronize()` has been a no-op since iOS 7) but it is inference from documentation, not a measurement. If cfprefsd behaves worse than that under repeated large writes — or if iOS 16's pre-swift-foundation `JSONEncoder` is materially slower than the one here — this jumps back toward 0.6-1.0 s per page and becomes unambiguously the #1 item. One Instruments trace of a folder open would settle it. (Since #2 landed the page pays one encode and one write whatever cfprefsd does, so even the pessimistic case is a few milliseconds.)
2. **`LayoutAudit` (#7).** Completely unmeasured, and unmeasurable from Linux — there is no UIKit here. `hasAmbiguousLayout` × a few hundred views × 90 sweeps on the main thread during launch and first scroll could be nothing, or it could be the only real dropped frame in the product. I am recommending the `#if DEBUG` on the grounds that it costs one line and has no user-facing value, not on the strength of a number I do not have.
3. **Whole-message `BODY.PEEK[]` on open (recorded, not scheduled).** This depends entirely on two things nobody here can see: what fraction of his mail is multi-megabyte, and what his uplink actually is. On a slow line with photo-heavy correspondence this outranks everything above it. On ordinary 20-60 KB letters it is a 20 ms non-issue. The honest position is that fixing #1 makes the wait *explained*, which is most of the felt damage, and the `RFC822.SIZE` gate should wait for real evidence about his mailbox.

One more calibration caveat worth stating: the A10-vs-A12 question is unresolved. Several numbers above were originally scaled 3-5x for "an old iPad"; on the evidence that this host is roughly A12-class, 1-1.5x is the better guess. If his device turns out to be an A10 or older with 2 GB of RAM, the memory items (`TLSConnection` retention, the `fetchAttachmentData` cache proposal) get more serious relative to the CPU items, because jetsam and cold relaunches start to dominate what he feels.
